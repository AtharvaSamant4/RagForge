# Security boundaries and launch requirements

This is a production-oriented MVP foundation, **not a production-certified service**.

Implemented: per-user ownership, project-first authorization on all private endpoints, credential scopes, hashed random API/session/widget tokens, PBKDF2-SHA256 passwords, HttpOnly SameSite=Strict sessions, browser Origin checks for cookie mutations, persisted atomic request limits, bounded request bodies, extension/signature/encoding validation, bounded DOCX expansion, randomized upload paths, foreign-key deletion, leased worker jobs, safe client error messages, prompt-injection boundaries and exact supporting-quote validation for hosted generation. Logs omit request/response bodies, tokens, questions, document contents and query strings. Compose only binds public services to loopback; the database has no host port.

Publishing a widget is an explicit public-data decision: it exposes answers and cited passages from **all** ready documents in that project. Its token is a public query capability, not a secret suitable for private documents. Allowed origins and CSP frame-ancestors constrain embedding, but cannot prevent a token holder from making server-side requests. Revoking/rotating publication invalidates old embeds. Public queries have separate project and IP budgets and do not expose conversations or administrative endpoints. The iframe token travels in the URL fragment and API Authorization headers, so it is not sent in request URLs or referrers. Referrer-Policy adds another boundary; production gateways must also avoid logging authorization headers. The generated iframe serves CSP on its own response and renders answers with textContent.

Deleting a document removes chunks, jobs and the stored file. To remove cached source text, it also clears project conversations, retained query counters and stored evaluation runs. Evaluation cases referring to that document are removed. Operator backups and previously delivered answers require separate retention policies. Files left by a process crash between filesystem write and DB commit may need operator reconciliation; there is no orphan-file sweeper yet.

Before internet exposure: provide TLS and secure cookies, disable or gate registration, change the database password, add email verification/password reset/SSO, enforce total storage and model-spend quotas, deploy parsers in resource-limited isolated processes, add malware scanning and PDF decompression/time limits, deploy encrypted storage and backups, implement audit/event retention and deletion policies, add monitoring/alerts, review dependencies, pen-test tenant boundaries and add provider-specific concurrency/cost controls. Database limits are a baseline; use a gateway for traffic and connection limits. The app trusts the direct client IP and deliberately ignores forwarding headers by default.

Local mode supports one worker. Use PostgreSQL for multiple workers. The claim token rejects stale worker commits; the lease renews between embedding batches. Very slow parsing can outlive a lease and duplicate work; stale output cannot replace a later attempt. Index publication is transactional. Retrieval skips documents queued for rebuilding and does not report a failed rebuild as successful ingestion.

Prompt injection cannot be fully solved by a system prompt. Documents are never executed and the local extractive provider does not follow instructions. The hosted provider has no tools, receives explicit untrusted-source boundaries, and must return exact source quotes. Quote existence verifies provenance, **not entailment or truth**. Human review and stronger semantic evaluations remain necessary for sensitive uses.
